# دليل الـ Backend (لمطوّر Frontend)

هذا الدليل يشرح ما بُني في `Qeeva-Backend` بلغة بسيطة. الكلمات التقنية تبقى بالإنجليزية لأنك
ستراها في الكود. آخر تحديث: 2026-11-14.

## 1) ما الذي بُني حتى الآن؟

الأساس فقط، وليس التطبيق كاملًا:

- **التحقق من الدخول:** Django يتأكد أن الـ token الذي يرسله Angular صادر فعلًا من Supabase.
- **نقطتا API فقط:** `GET /api/health/` (عامة، تقول إن الخادم يعمل) و`GET /api/me/` (تعيد
  رقم المستخدم المُتحقَّق منه).
- **ثلاثة جداول للحساب:** `profiles` و`username_reservations` و`user_settings`.
- **اختبارات** تتحقق من قواعد الأمان وقواعد الجداول.

لم تُبنَ بعد: جداول المال (الأشهر والعناصر)، ونقاط API لها، والحسابات (الصيغ).

## 2) خريطة المجلدات

```
Qeeva-Backend/
  core/              الإعدادات (كلها من متغيرات البيئة) وملف الروابط الرئيسي
  common/            أشياء مشتركة بين كل التطبيقات
    auth.py            التحقق من token الخاص بـ Supabase
    ownership.py       القاعدة: "المستخدم يرى بياناته فقط" (for_user)
    db.py              دالة تقفل الجدول أمام Supabase Data API
  apps/accounts/     الحساب: models.py (الجداول) وmigrations/ (تاريخ تغييرات القاعدة)
  apps/finance/      المال: الأشهر، الدخل، الأصناف، البطاقات (بدون API حتى الآن)
  conftest.py        إعدادات الاختبارات المشتركة
  docker-compose.yml قاعدة PostgreSQL مؤقتة للاختبار
  AGENTS.md          دليل للذكاء الاصطناعي الذي يعمل معك (ذاكرته بين الجلسات)
  docs/              هذا الدليل وسجل القرارات وخريطة الجداول
```

**مقارنة:** `models.py` مثل `interface` في TypeScript، لكنه يُنشئ جدولًا حقيقيًا. و`migrations/`
مثل سجل Git لشكل قاعدة البيانات.

## 3) ماذا يحدث عندما يطلب Angular شيئًا؟

```
1. المستخدم يسجل دخوله في Supabase  ->  يحصل على token (JWT)
2. Angular يرسل الطلب:  Authorization: Bearer <token>
3. Django يجلب المفتاح العام من Supabase (JWKS) ويتحقق من توقيع الـ token
4. إذا فسد الـ token أو انتهى أو لم يصدر من Supabase  ->  401 (ممنوع)
5. إذا صح  ->  Django يعرف "من هذا المستخدم" (رقمه uuid) ويكمل
6. كل قراءة للبيانات تمر عبر for_user(...): يرى المستخدم صفوفه فقط
```

الـ API **مقفل افتراضيًا**: أي نقطة جديدة تحتاج token إلا إن قلنا غير ذلك صراحة (مثل `/health/`).

## 4) جداول الحساب

| الجدول | ما يحمله | أهم قواعده |
|---|---|---|
| `profiles` | اسم المستخدم والاسم الظاهر والدور والحالة | الاسم 3 إلى 20 حرفًا إنجليزيًا/أرقام/`_`، ولا يتكرر (`Bob` = `bob`) |
| `username_reservations` | أسماء قديمة محجوزة 30 يومًا | تبقى حتى لو حُذف صاحبها القديم |
| `user_settings` | Regular/Advanced والمنطقة الزمنية واللغة | صف واحد لكل مستخدم |

القواعد موجودة **داخل قاعدة البيانات نفسها** (وليس في الكود فقط). فحتى لو أخطأ الكود، ترفض
القاعدة البيانات الخاطئة.

عند حذف مستخدم من Supabase: القاعدة تحذف ملفه وإعداداته تلقائيًا، أما الأسماء المحجوزة فتبقى.

## 5) كلمات ستسمعها

- **Migration:** ملف يصف تغييرًا في شكل القاعدة (إضافة جدول مثلًا). نُنشئه ولا نعدّل القاعدة بيدنا.
- **Constraint:** قاعدة تفرضها القاعدة على كل صف (مثل `validators` لكن داخل الجدول).
- **RLS (Row Level Security):** قفل يمنع من يتصل بقاعدة Supabase من المتصفح مباشرة. نفعّله على كل
  جدول بلا أي استثناء، فلا يصل إليه إلا Django.
- **JWT / token:** بطاقة دخول موقّعة تحمل رقم المستخدم.
- **JWKS:** قائمة المفاتيح العامة التي نتحقق بها من توقيع البطاقة.
- **Docker:** برنامج يشغّل أشياء (مثل PostgreSQL) داخل صندوق معزول بدل تثبيتها على جهازك.
- **pytest:** يشغّل الاختبارات. **ruff / mypy:** يفحصان الأسلوب والأنواع (مثل ESLint وtsc).
- **CI (GitHub Actions):** يشغّل الفحوص نفسها على GitHub عند كل رفع.

## 6) الأوامر (من داخل `Qeeva-Backend` وبعد تفعيل venv)

```powershell
docker compose up -d --wait        # تشغيل قاعدة الاختبار (Docker Desktop مفتوح)
$env:QEEVA_TEST_DATABASE_URL = "postgresql://postgres:test@127.0.0.1:5433/postgres"
python -m pytest                   # كل الاختبارات
python -m pytest --reuse-db        # يُبقي قاعدة test_postgres لتراها في pgAdmin
docker compose down                # إيقاف القاعدة وحذف بياناتها

ruff check .                       # فحص الأسلوب
ruff format --check .              # فحص التنسيق
mypy .                             # فحص الأنواع
```

## 7) إذا حدثت مشكلة

| العَرَض | السبب والحل |
|---|---|
| `73 skipped` | لم تضع `QEEVA_TEST_DATABASE_URL`. هذا ليس نجاحًا، فاتبع أمر Docker أعلاه. |
| الاتصال بـ `127.0.0.1:5433` مرفوض | Docker Desktop مغلق أو الحاوية متوقفة: `docker compose up -d --wait`. |
| `port is already allocated` | شيء آخر يستعمل 5433. غيّر الرقم في `docker-compose.yml` وفي المتغير. |
| الاختبارات بطيئة جدًا (دقائق) | السبب الذي وجدناه بالقياس: الاتصال عبر الاسم `localhost` يأخذ حوالي 15 ثانية لكل اتصال على ويندوز، وعبر `127.0.0.1` حوالي 0.02 ثانية. الكود صار يحوّل `localhost` تلقائيًا، لكن اكتب `127.0.0.1` دائمًا. إن بقيت بطيئة: `python -m pytest --durations=5 -q` وأرسل لنا النتيجة. |
| `settings are not configured` أو `ImproperlyConfigured` عند `pytest` | أنت في المجلد الخطأ (جذر المشروع). ادخل أولًا `cd Qeeva-Backend` ثم شغّل `python -m pytest`. |
| فشل اختبار عندك ولا يفشل عندي | أرسل لنا الخطأ كاملًا. لا تعدّل الاختبار. |

## 8) قواعد لا نكسرها

- لا نضع أسرارًا (`.env`) في Git.
- لا نغيّر Supabase إلا بعد موافقتك الصريحة على كل تغيير، وعلى `qeeva-dev` فقط.
- الجداول تتغير بـ migrations فقط.
- لا نبني نقاط API جديدة قبل أن تغيّر نطاق العمل بنفسك.
